# Конкуренты: что показала декомпиляция EMI и REI

Дата: 09.11.2026. Метод: CFR 0.152 по jar под Minecraft 1.21.1 NeoForge.

| Мод | Версия | Файл | sha1 |
|---|---|---|---|
| EMI | 1.1.24 (13.05.2026) | `research/jars/emi-1.1.24+1.21.1+neoforge.jar` | `3fd494b3…6738a` |
| REI | 16.0.799 (16.02.2025) | `research/jars/RoughlyEnoughItems-16.0.799-neoforge.jar` | `58e3de0c…c03f9` |

Jar взяты с Modrinth (те же сборки авторов, что и на CurseForge; у Modrinth открытый API и контрольные суммы). Декомпилированный код: `research/src/emi`, `research/src/rei`. Ссылки ниже даны как `файл:строка` относительно `research/src/emi/dev/emi/emi/` и `research/src/rei/me/shedaniel/rei/`.

JEI не декомпилировали: столбец JEI в таблице концепта остаётся со слов, не по коду.

## 1. Слой совместимости с плагинами JEI

### EMI: это мост, а не реализация API

В концепте было написано «реализация `IModPlugin`, `IRecipeCategory`, `IRecipeTransferHandler` JEI поверх собственного ядра (как у EMI)». Код показывает другое.

- `JemiPlugin` сам является плагином JEI: `@JeiPlugin class JemiPlugin implements IModPlugin, EmiPlugin` (`jemi/JemiPlugin.java:138-141`). Он подключается, только если JEI установлен: `if (EmiAgnos.isModLoaded("jei")) plugins.add(new JemiPlugin())` (`runtime/EmiReloadManager.java:183-184`).
- JEI загружается полностью сам, вызывает плагины модов, строит свой рантайм. EMI ждёт его в своём потоке перезагрузки: `while (runtime == null) Thread.sleep(100)` (`JemiPlugin.java:181-185`).
- Дальше EMI перекачивает данные из `IJeiRuntime`:
  - ингредиенты нестандартных типов из `getIngredientManager()` в обёртку `JemiStack` (рендер и тултип делегируются `IIngredientRenderer` JEI) (`JemiPlugin.java:205-212`, `jemi/JemiStack.java`);
  - скрытые ингредиенты через `getIngredientVisibility()` (`:213-224`);
  - подтипы через `ISubtypeManager` (`:387-427`);
  - категории через `createRecipeCategoryLookup().includeHidden()` (`:244`), катализаторы, рецепты (`:283-291`);
  - ванильные типы JEI сопоставляются с родными категориями EMI (`:229-241`), info-рецепты склеиваются в `EmiInfoRecipe` (`:299-327`).
- Категория, у мода которой уже есть родной плагин EMI, пропускается (`:268-275`).
- Рецепт JEI рисуется самим JEI: `category.setRecipe(...)` для раскладки слотов, `category.draw(...)` и `getBackground().draw(...)` для фона, `category.getTooltip`, `handleInput` (`jemi/JemiRecipe.java:156-235`). Слоты EMI ставит свои поверх (`JemiSlotWidget`, `JemiTankWidget`), чтобы работали клики, избранное и дерево.
- Перенос в слоты для таких рецептов исполняет обработчик JEI: `runtime.getRecipeTransferManager().getRecipeTransferHandler(menu, category)` → `handler.transferRecipe(...)` (`JemiPlugin.java:429-435`, `jemi/JemiRecipeHandler.java:138-154`). Ошибки JEI (`IRecipeTransferError`) превращаются в подсветку слотов и кнопки (`:101-136`).
- Интерфейс JEI прячется штатным API: `IRuntimeRegistration.setIngredientListOverlay / setBookmarkOverlay / setRecipesGui / setIngredientFilter` получают реализации-заглушки, которые отвечают состоянием EMI (`JemiPlugin.java:162-167`, `jemi/runtime/*`). Благодаря этому моды, которые спрашивают у JEI «что под курсором» или просят «покажи рецепты», попадают в EMI.
- Через JEI же подхватываются зоны исключения чужих экранов, кликабельные ингредиенты и ghost-слоты для перетаскивания (`JemiPlugin.java:192-202`, `jemi/runtime/JemiDragDropHandler.java`).
- Чтобы JEI не делал лишнюю работу, EMI миксином в **внутренний** класс JEI `mezz.jei.library.load.PluginCaller` пропускает часть фаз собственных плагинов JEI и целиком плагины модов, у которых есть родной плагин EMI (`mixin/jei/PluginCallerMixin.java`). Это не API, при обновлении JEI может сломаться.

Объём слоя: 29 файлов, около 3 000 строк.

### REI: слоя нет

- Строки `mezz.jei` в jar нет. `isJEICompatibilityLayerEnabled()` помечен `@Deprecated(forRemoval=true)` и всегда возвращает `false` (`api/client/config/ConfigObject.java:248-250`).
- Остались следы: поле `ClientInternals.jeiCompatMods` без заполнения (`impl/ClientInternals.java:102`), ключи перевода `text.rei.jei_compat*`.
- Точка расширения есть: сторонний мод может отдать плагины через `@REIPluginLoader` + `REIPluginProvider` (`forge/PluginDetectorImpl.java:84-88`). Существует ли под 1.21.1 сторонний мод-адаптер (REIPC), не проверено.

### Сторонний слой для EMI

На Modrinth есть TooManyRecipeViewers (TMRV), описание: «A compatibility layer for running JEI plugins with EMI», NeoForge 1.21.1, лицензия OSL-3.0. Код не смотрели. Лицензия копилефтная: заимствовать код оттуда нельзя, если RYScope выходит под другой лицензией.

### Развилка для RYScope

| | A. Мост поверх установленного JEI (как EMI) | B. Своя реализация API JEI (JEI не нужен) |
|---|---|---|
| Что ставит игрок | RYScope + JEI | только RYScope |
| Объём работы | около 3 000 строк, API официальное | реализовать весь `mezz.jei.api`: рантайм, реестры, хелперы, drawable, подтипы, перенос |
| Совместимость | максимальная: плагины выполняет настоящий JEI | ломаются моды, которые лезут во внутренности JEI |
| Цена | JEI грузится параллельно (время и память), его загрузку мы не контролируем | нельзя ставить рядом с настоящим JEI (те же пакеты и modid `jei`) |
| «Ноль фризов» | наш интерфейс открывается сразу, рецепты JEI появляются, когда JEI закончит | полностью под нашим контролем |

Дополнение от 09.11.2026: выбран третий путь, которого в таблице нет. JEI (лицензия MIT) вложен в jar RYScope и запускается в фоновом потоке. Игрок ставит один файл, совместимость полная. Подробности и замеры: `06-dev-log.md`, цикл 7.

Первоначальное решение для MVP: **A**, с JEI как необязательной зависимостью. Без JEI мод работает на своих категориях (ванильные рецепты + родные плагины), с JEI подхватывает всё остальное. Шов делается так, чтобы источник «рецепты из JEI» был одним из поставщиков снимка: тогда вариант B позже подменяет поставщика, а не ядро.

Формулировку дорожной карты «заменить JEI в любой сборке без потерь» надо читать как «заменить интерфейс JEI»: сам JEI остаётся в сборке как библиотека плагинов.

## 2. Перенос рецепта в слоты

### EMI

- API: `EmiRecipeHandler<T>` (`getInventory`, `supportsRecipe`, `canCraft`, `craft`, `render`) и упрощённый `StandardRecipeHandler` (`getInputSources`, `getCraftingSlots`, `getOutputSlot`) (`api/recipe/handler/*`). Регистрация по `MenuType`. Любой экран с `ResultSlot` получает обработчик автоматически (`registry/EmiRecipeFiller.java:106-111`).
- План считается на клиенте: для каждого ингредиента ищутся совпадения в слотах-источниках, выбирается вариант с наибольшим запасом (`EmiRecipeFiller.java:147-283`).
- Пакет `emi:fill_recipe`: id окна, действие, слоты-источники, слоты сетки, слот результата, список стеков. Id рецепта не передаётся (`network/FillRecipeC2SPacket.java:37-42`).
- Сервер проверяет id окна, диапазоны слотов, `mayPickup` / `mayPlace`, при нехватке возвращает предметы. Соответствие рецепту не проверяется (`:101-179`).
- Если мода на сервере нет, перенос эмулируется обычными кликами по слотам (`StandardRecipeHandler.java:70-72`, `EmiRecipeFiller.java:285-341`).
- Shift = максимум. Есть «скрафтить сразу» в инвентарь или на курсор для стеков из сайдбара (`config/EmiConfig.java:309-323`).

### REI

- API: `TransferHandler.handle(Context)` с результатом (успех, неприменимо, ошибка с цветом кнопки и тултипом недостающего) и упрощённый `SimpleTransferHandler.create(menu, category, inputSlots)` (`api/client/registry/transfer/*`).
- Пакет `move_items_new`: id категории, shift, NBT со входами и слотами. Без REI на сервере перенос не работает (`impl/client/transfer/SimpleTransferHandlerImpl.java:73-98`).
- Сервер сам подбирает предметы через `RecipeFinder`, повреждённые, зачарованные и переименованные не берёт (`impl/common/transfer/InputSlotCrafter.java:49-145`).
- Недостающие слоты заливаются красным, кнопка краснеет, тултип перечисляет недостающее.

### Что берём

- Свой обработчик по `MenuType` с тремя списками слотов, автообработчик для экранов с `ResultSlot`.
- Запасной путь кликами, когда мода нет на сервере: обязательное условие «ставится в любую сборку».
- Для категорий из JEI перенос делегируется обработчику JEI.
- Отличие, которое можно себе позволить: сервер получает id рецепта и сам проверяет, что раскладка ему соответствует. Ни EMI, ни REI этого не делают.

## 3. Потоки, кэш, перезагрузка

| | EMI | REI |
|---|---|---|
| Поток перезагрузки | `new Thread(ReloadWorker)` (`runtime/EmiReloadManager.java:107-109`) | один daemon-поток `REI-ReloadPlugins`, отключается опцией (`impl/common/plugins/ReloadManagerImpl.java:44-46`) |
| Триггер | оба события: рецепты и теги (`EmiReloadManager.java:53-71`) | пакет рецептов + событие, debounce 1 с |
| Прерывание | флаг `restart`, до 3 повторов | флаг, ожидание до 5 с |
| Что в главном потоке | сбор креативных вкладок (`registry/EmiStackList.java:122-129`), пересчёт «крафтабельного» из рендера раз в 50–400 мс | плагины с `shouldBeForcefullyDoneOnMainThread` |
| Кэш на диск | нет | нет |
| Инкрементальность | нет, всегда полная очистка | только для правил фильтрации, не для плагинов |
| Поиск | новый поток на каждое изменение текста, отмена раз в 1024 элемента (`search/EmiSearch.java:151-208`) | пул до 3 потоков, партиции, отмена (`impl/client/search/AsyncSearchManager.java:41`) |

Вывод: фоновая индексация у обоих уже есть, это не отличие. Отличия RYScope: кэш индекса на диск и инкрементальная перезагрузка. При этом сбор креативных вкладок в главном потоке у EMI показывает реальное ограничение: `CreativeModeTab.buildContents` нельзя безопасно звать вне главного потока, это надо учесть (делать порциями по кадрам или брать из кэша).

## 4. Поиск

| | EMI | REI | RYScope (концепт) |
|---|---|---|---|
| Мод | `@` | `@` | `@` |
| Тег | `#` | `$` | `#` |
| Тултип | `$` | `#` | `$` |
| Id | в имени | `*` | через имя |
| Regex | `/.../` | `r/.../` | нет в концепте |
| Отрицание, ИЛИ, кавычки | `-`, `\|`, `"..."` | `-`, `\|`, `"..."` | то же |
| Индекс | суффиксные массивы (подстрока) | `String.contains` с кэшем по типу аргумента | суффиксный индекс + fuzzy |
| Алиасы | да, из ресурспака `assets/emi/aliases/*.json` | нет | добавить |
| Языки | только текущий | только текущий; пиньинь и подобное для `zh_*` | все загруженные |
| Опечатки, транслит | нет | нет | да |

Префиксы у EMI и REI для тега и тултипа противоположны. RYScope берёт вариант JEI/EMI (`#` тег, `$` тултип) как более распространённый; regex `/.../` стоит добавить, чтобы привычка игроков EMI сохранялась.

## 6. Что стоит перенять

- Тег `c:hidden_from_recipe_viewers`: его уже уважают оба конкурента, авторы модов на него рассчитывают.
- Данные из ресурспака в духе EMI: алиасы, рецепты по умолчанию для дерева, порядок и состав списка, исключения тегов. Авторы сборок это уже умеют.
- Запасной перенос кликами без мода на сервере (EMI).
- Подсветка в открытом контейнере слотов, подходящих под поисковый запрос (EMI, `EmiSearchWidget.java:59`).
- Экран производительности плагинов (REI): сразу видно, какой плагин тормозит загрузку.
- Батчинг рендера иконок (EMI, `screen/StackBatcher.java`).
- Ctrl+клик по предмету в списке = сразу перенос рецепта (REI).

## 7. Чего проверка не покрыла

- JEI не декомпилирован: в каком потоке он грузится, как устроен его перенос на сервере.
- Аддоны EMI и REI (лут, руды) не смотрели: «нет встроенного» не значит «нет в экосистеме».
- TMRV и REIPC по коду не смотрели.
- Планировщик и сравнение маршрутов у конкурентов отдельным поиском не искали; вывод «нет» сделан по отсутствию энергии и времени в модели рецепта EMI и по списку экранов.
